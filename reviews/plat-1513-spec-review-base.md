# SR-20261113000901: Base spec review of SOUP promotion, advisory join and report (FR-141..FR-144, NFR-030)

## Summary

Ticket: PLAT-1513 (also the spec PLAT-1515 is blocked on). The base checklist was run over the PR #837 diff only (`git diff origin/main...HEAD`: FR-141..FR-144, NFR-030, two indexes and `spec/spec.md`). The PR is checked against the PLAT-1513 and PLAT-1515 ACs, against the merged `agent-ix/spec-objects-security` FR-009..FR-012 and NFR-001 (origin/main), and against quoin's FR-034, FR-041, FR-046, FR-133 and FR-135. Claims about the existing requirements were checked against the quoin source at the PR base: `quoin-evidence` `adapters/sbom.rs`, `adapters/sarif.rs` (`parse_cargo_audit`), `adapters/cargo_deny.rs` and `types/scan.rs`, and `quoin-cli` `discharge.rs`.

`quire validate --scope . <the 8 changed files>` exits 0, and the changed files raise no EARS or quality warning. A full `spec/**/*.md` run fails on one document, FR-113-AC-6 (a row-width error), which is on main and not in this diff.

Field names agree with spec-objects-security: `purl`, `serves`, `known_anomalies`, `support_status`, `end_of_support`, `disposition_clause` and `finding_refs`. `SoupSupportStatus` is used by name and not restated. `license_fact_ref` is not written, which is correct. Nothing writes a key outside the closed schema. No network fetch (FR-143), no wall clock (an explicit `--as-of`), no derived score (NFR-030, FR-142-AC-9, FR-144-AC-10). No pin, digest or tracking record, no paywalled standard name, no roadmap content, and nothing copied across repos.

Clean units: FR-141-AC-2/3/4/5/7/8/9/10, FR-142-AC-3/4/6/7/8/9/10/11, FR-143-AC-1..AC-8 (beyond the integrity findings), FR-144-AC-1..AC-11 (beyond FND-001) and NFR-030-AC-1..AC-3.

Answers to the author's open questions. The names `quoin soup promote` and `quoin soup report` are fine. On where promote writes, see FND-008. A per-invocation `--support` file with no new record type is acceptable for V1 and breaks no AC. One `disposition_clause` per record does not satisfy 'person-owned disposition for each unresolved advisory', see FND-002. Crate-name+version matching is acceptable and has to be the primary rule, see FND-003.

## Verdict

FAIL. FND-001 and FND-002 are high. The PR is mergeable once FND-001..FND-009 are fixed in this PR.

| FND-001 | high | The FR-133 partition cannot be computed from the inputs this PR gives the report. FR-133 derives the partition from a live clause-binding-v1 report plus facts stored at discharge/<authority>/<id>/<version>/<clause>.json, and `quoin discharge` requires `--binding`. A `disposition_clause` is a bare clause id with no clause-set key, and FR-144 takes only `--repo`, `--as-of` and `--support`, and says it SHALL read only soup_record files, retained scans, stored facts and `--support` (FR-144 line 37). There is no binding report, so the join cannot find the fact or know whether the clause binds (a fact on a not-binding clause is 'unused', never a disposition). FR-141 also fills `disposition_clause` from `--discharges <obligation-id>`, which is checked against spec obligations (FR-041-AC-8), not clause-set clause ids. Fix: give `quoin soup report` a `--binding <clause-binding-v1>` input, add it to the FR-144 read-list, state that `disposition_clause` names a clause of that binding report, and add an unresolved reason for a clause that is unknown to the binding report or does not bind. | spec/functional/FR-142-advisory-join-onto-soup-records.md:44 |
| FND-002 | high | One `disposition_clause` per record resolves every advisory attached to that record. That includes advisories first reported after the fact was attested, which no person has reviewed. A record accepted for RUSTSEC-A shows a later RUSTSEC-B as resolved, with A's decision, rationale and attester. This does not meet the ticket AC 'the person-owned disposition for each unresolved advisory' (author open question 4: as written, no). Fix (author's choice): key the decision per advisory without a new record type. For example, advisory A on a record is resolved only by a fact under clause `<disposition_clause>/<rule-id>`, so FR-046's shape and the soup_record schema stay unchanged. Or keep record-level clauses, but treat an advisory as unresolved ('disposition predates scan') when the retained scan that reports it is newer than the fact's `attestedAt`, and state that limit in FR-142. | spec/functional/FR-142-advisory-join-onto-soup-records.md:44-46 |
| FND-003 | medium | FR-034 findings carry no purl. The `Finding` record is {ruleId, severity, message, path, line, traceIds}. The cargo-audit adapter (`parse_cargo_audit`) and the cargo-deny adapter (`diagnostic_finding`) both put the crate as `name@version` in `Finding.path`. So 'a package whose purl equals a fixture record's purl' (AC-1, Behavior line 33) can never be constructed, and the fallback on line 34 is the only path for both adapters. Answer to author question 5: crate-name+version matching is right, but make it the primary rule. State it as: `Finding.path` `<name>@<version>` matches a record whose purl is `pkg:cargo/<name>@<version>` (state whether qualifiers or a subpath are ignored), and a path with no version matches nothing and is listed unmatched. Reword AC-1 to match. | spec/functional/FR-142-advisory-join-onto-soup-records.md:33-34 |
| FND-004 | medium | cargo-deny output that FR-034-AC-23 or AC-25 refuses is refused when it is recorded, so no FindingRecord is written (FR-034-CON-1). A 'retained scan ... that FR-034-AC-25 would refuse' therefore cannot exist in the store, so the Behavior on lines 39-40 is vacuous. AC-5 cannot be set up through `quoin evidence record`, and only a hand-written store file could reach it. Fix: state that a refused recording leaves no retained scan, so the join reports that tool's scan as not run. Restate AC-5 as: recording the over-counting log through `quoin evidence record --tool cargo-deny` is refused, and the report then shows cargo-deny not run, never clean. | spec/functional/FR-142-advisory-join-onto-soup-records.md:39-40 |
| FND-005 | medium | The spec does not say which retained scans the join reads, or how it decides that 'a scan' was not run. The store can hold several FindingRecords per tool and suite, and nothing names the expected scans. Two implementers could read every scan, or the newest per suite, or the newest per tool, and get different attachments and a different not-run list. Fix: for each of cargo-audit and cargo-deny, read the newest FindingRecord whose `tool` is that tool, ordered by `timestamp` (FR-034-CON-4). No such record means that tool's scan is reported not run. | spec/functional/FR-142-advisory-join-onto-soup-records.md:32 |
| FND-006 | medium | 'Advisory findings' has no selection rule. A cargo-deny FindingRecord also holds ban, licence and source diagnostics: rule id is the check `code`, or `unclassified`, and the record does not keep whether an id came from `advisory.id`. cargo-audit findings include the warning kinds `unmaintained`, `yanked` and `unsound`. Fix: say which findings count as advisories, for example a rule id of RUSTSEC/GHSA form, or every finding of both tools, and whether cargo-audit warnings are included. Then cover the excluded case in an AC. | spec/functional/FR-142-advisory-join-onto-soup-records.md:32 |
| FND-007 | medium | Promotion conflicts with the PLAT-1515 AC that this spec unblocks: 'Component count of records equals the fixture SBOM component count'. FR-141 skips components with no purl, merges duplicate purls and leaves existing records unchanged, so the record count can be lower than the component count. No AC accounts for each component. Fix: add an AC that `created + unchanged + skipped (no purl) + merged duplicates == components read by the FR-041 adapter`, shown in the report. Restate the PLAT-1515 AC against it. | spec/functional/FR-141-promote-sbom-components-to-soup-records.md:32 |
| FND-008 | medium | FR-141 does not say where a new record is written (directory and file name) or where 'a record for the purl already exists' is looked for (author open question 2). If the lookup covers only the output directory, promote can create a second record for a purl already recorded elsewhere in the repository, and FR-144-AC-6 and FR-009's duplicate-purl check then refuse the report. Fix: require `--out <dir>` (or state a fixed convention), give the file name as a function of the purl, and look up existing records in every soup_record of the repository, the same set FR-144 reads. | spec/functional/FR-141-promote-sbom-components-to-soup-records.md:32 |
| FND-009 | medium | Record identity is the purl, and a purl carries the version (`pkg:cargo/a@1`), so a version bump gives a new purl and a new record, not a 'difference'. AC-6 can only happen when the record's `version` field disagrees with its own purl, or when a purl has no version. The common case is not specified: after an upgrade, the old record stays and no longer appears in the SBOM, and nothing reports it. Fix: list records in the scanned set whose purl is not in the SBOM as 'not in this document'. Restate AC-6 on the reachable case, or drop it. | spec/functional/FR-141-promote-sbom-components-to-soup-records.md:44-45 |
